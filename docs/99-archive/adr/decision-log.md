# Architecture Decision Log

> 关键决策记录。只增不改。

---

## 0001 — Obsidian 作为长期记忆主库

- **日期**：2026-06-09
- **状态**：已确认

**上下文**：需要决定长期记忆的最终宿主。PostgreSQL 是运行时主库，但长期可视化、人工审计和跨机器迁移需要可读文件格式。

**决策**：Obsidian Vault 作为长期记忆主库，PostgreSQL 作为运行时主库。两者通过同步脚本保持一致。

**后果**：需要维护双向同步逻辑；增加了一次写入路径（PG + 文件），但获得了人工可读和可迁移性。

---

## 0002 — Event-First 设计

- **日期**：2026-06-09
- **状态**：已确认

**上下文**：需要统一的输入模型，避免不同渠道各自写入内存。

**决策**：所有输入必须转换为 Event 后再进入系统，Event 是唯一事实源。原始事件不可修改。

**后果**：新增渠道只需实现 Event 转换器；查询时需从 Event 重建状态，增加一间接层。

---

## 0003 — 单 Agent + 多 Operator

- **日期**：2026-06-09
- **状态**：已确认

**上下文**：需要认知分工但又不希望多 Agent 复杂度和成本。

**决策**：认知层按功能拆为 Companion / Researcher / Critic / Archivist 等 Operator，但物理上在单次 LLM 调用内完成，通过结构化输出字段区分。

**后果**：不能并行执行；单次请求的 token 消耗更高；但避免了多 Agent 编排的复杂性和延迟爆炸。

---

## 0004 — 单体优先

- **日期**：2026-06-09
- **状态**：已确认

**上下文**：MVP 阶段需要快速验证价值，微服务会拖慢开发。

**决策**：MVP 阶段保持单体架构。所有模块在同一个 Node.js 进程中运行。拆分到独立服务仅当出现以下任一情况时考虑：a) 性能瓶颈可定位到单一模块；b) 需要独立部署不同生命周期；c) 团队 > 1 人。

**后果**：短期开发效率高；长期可能存在模块耦合风险，但可以通过良好接口定义缓解。
